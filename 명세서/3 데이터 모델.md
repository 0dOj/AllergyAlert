# 3. 데이터 모델 (1)

> 2026-09-30 실측(C005 1,200행 · C002 1,000행) 기준으로 확정한 스키마. 근거 수치는 8. 리스크 · 데이터 한계 의 R-8 참조.
> 

## 설계 원칙

- 원재료 **원문 문자열을 그대로 보관**한다. 파싱본을 저장하지 않는다 — 매칭 규칙이 바뀌면 재계산하면 된다
- 알레르겐 동의어·제외어는 **코드가 아니라 DB**에 둔다. 사전 수정에 배포가 필요 없어야 한다
- 모든 번호(바코드·품목보고번호)는 `TEXT`. 숫자형은 절대 금지
- 날짜는 `YYYYMMDD` 문자열. API가 주는 빈 문자열은 적재 시 `NULL`로 정규화
- 조인은 느슨하게. FK 제약을 걸지 않는다 (실측 조인율 약 47%)

## 핵심 구조 — 바코드와 품목보고를 분리

품목보고번호 하나에 바코드가 여러 개 붙는다(용량별 제품, 실측 최대 4개). 한 테이블로는 표현할 수 없다.

| 테이블 | 출처 | 규모 | 역할 |
| --- | --- | --- | --- |
| `barcodes` | C005 + I2570 | 약 31만 | 바코드 → 품목보고번호 색인 |
| `product_reports` | C002 | 107만 | 원재료를 가진 마스터 |

조회 경로는 `barcodes.barcode` → `report_no` → `product_reports.raw_material`.

C005에는 있지만 C002에 없는 제품(포장육·수입식품)이 절반가량이므로, `barcodes`도 제품명·제조사를 자체 보유한다. 원재료만 없을 뿐 제품 정보는 보여줄 수 있어야 한다.

### term_rules

알레르겐에 속하지 않는 **전역 규칙**. `혼합제제`·`소스`·`기타가공품`은 어느 알레르겐과도 무관하게 `caution`을 만든다. 그래서 `allergen_keywords`에 얹을 수 없고 별도 테이블이 필요하다. 이 테이블은 다른 테이블과 관계가 없는 독립 참조 테이블이다.

| 컬럼 | 타입 | 설명 |  |
| --- | --- | --- | --- |
| id | INTEGER PK |  |  |
| pattern | TEXT | 매칭할 문자열. `$`로 시작하면 접미사 (예: `$향`) |  |
| rule_type | TEXT | `compound` / `flavor` / `ambiguous` |  |
| note | TEXT | 근거·빈도 메모 |  |
| rule_type | 의미 | 판정 영향 | 실측 규모 |
| --- | --- | --- | --- |
| `compound` | 하위 성분을 알 수 없는 복합원재료 | `unresolved`에 담고 `caution` | 가공품 6,214 · 복합조미식품 3,196 · 제제 2,790 · 소스 2,680 |
| `flavor` | 향료 — 해당 식품 단백질이 없을 수 있음 | `danger` → `caution`으로 낮춤 | 649종 4,957회 |
| `ambiguous` | 무엇인지 특정 불가 | `caution` | 또는 434 · 두류 294 · 식물성크림 530 |

코드에 정규식으로 박아도 동작하지만, DB에 두면 배포 없이 고칠 수 있다. 동의어 사전을 DB에 둔 것과 같은 이유다.

> **복합원재료라고 알레르겐 검사를 건너뛰면 안 된다.** `혼합분유`(96회)는 복합원재료이면서 동시에 우유다. 두 판정을 동시에 적용하고 `danger`를 우선한다.

## 바코드 정규화 규칙

저장할 때와 조회할 때 **반드시 같은 함수**를 통과시킨다.

1. 숫자가 아닌 문자 제거
2. 12자리면 앞에 `0`을 붙여 13자리로 (UPC-A → EAN-13)
3. 결과를 그대로 저장 / 조회

스캐너가 UPC-A를 12자리로 반환하는데 DB에는 13자리로 저장돼 있다. 이 변환을 빠뜨리면 수입 제품이 통째로 조회 실패한다. (실측상 12자리 바코드는 DB에 0건)

수동 입력 검증은 **숫자만, 8~13자리**로 느슨하게. 틀린 번호는 어차피 "조회 안 됨"으로 처리되므로 엄격하게 막을 이유가 없다.

스캐너 인식 포맷: `EAN_13`, `EAN_8`, `UPC_A`, `UPC_E`

## 적재 전략

1. 최초 1회 — `/file` 엔드포인트로 전체 덤프 후 일괄 적재
2. 이후 — `CHNG_DT` 기준 증분 (최대 7일 범위)
3. upsert 기준 — `barcodes`는 `(barcode, report_no, source)`, `product_reports`는 `report_no`
4. 빈 문자열은 `NULL`로 변환한 뒤 저장
5. 실행 이력은 `ingest_log`에 기록

## 인덱스

```sql
CREATE INDEX idx_barcodes_barcode   ON barcodes(barcode);
CREATE INDEX idx_barcodes_report    ON barcodes(report_no);
CREATE INDEX idx_barcodes_name      ON barcodes(product_name);
CREATE UNIQUE INDEX idx_barcodes_uq ON barcodes(barcode, report_no, source);
CREATE INDEX idx_reports_name       ON product_reports(product_name);
CREATE INDEX idx_kw_allergen        ON allergen_keywords(allergen_id);
CREATE INDEX idx_termrules_type     ON term_rules(rule_type);
```

`product_reports.report_no`는 PK라 별도 인덱스가 필요 없다.

제품명 검색은 `LIKE '%q%'`라 인덱스가 안 먹는다. 107만 행에서 느리면 FTS5 가상 테이블 도입을 검토한다.

## 시드 데이터

`seed.json` 에 실측 기반 초기 데이터가 있다.

| 항목 | 내용 |
| --- | --- |
| `allergens` | 22행 (법정 19항목, 조개류를 굴·전복·홍합으로 분리) |
| `allergen_keywords` | 동의어 약 200개 + 알레르겐별 제외어 약 40개 |
| `term_rules` | 복합원재료 17 · 향료 5 · 모호표기 5 |
| `products` | 개발용 샘플 10건 (실제 API 응답에서 가져온 원재료 문자열) |

> **제외어는 반드시 알레르겐별로 넣는다.** `메밀`은 밀(WHEAT)의 제외어이자 메밀(BUCKWHEAT)의 동의어다. 전역 제외어 목록을 만들면 메밀 알레르기가 영영 안 잡힌다.
> 

샘플 제품 10건은 판정 3종과 오탐·혼동 케이스를 고루 담고 있다 — 밀크초콜릿(밀 vs 우유), 메밀부침가루(밀 vs 메밀), 건스파게티(게 오탐), 땅콩 또는 견과류가공품(모호), 복숭아향(향료).

## 넣지 않기로 한 것

| 항목 | 이유 |
| --- | --- |
| `ingredient_tokens` (원재료 분해 테이블) | 매칭에 불필요. 약 870만 행을 만들 만한 값어치가 없다고 판단 |
| 생산중단 경고 UI | `end_dt`는 컬럼으로 보관하되 화면에 배너로 띄우지 않는다. 실측 47.8%가 해당돼 배너가 무감각해진다 |
| 판정 결과 캐시 테이블 | 프로필이 바뀌면 전부 무효화된다. 매칭이 순수 함수라 매번 계산해도 빠르다 |
